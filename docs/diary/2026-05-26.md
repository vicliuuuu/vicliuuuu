# VLM 自动驾驶场景微调对话记录

导出日期：2026-05-26

## 1. VLM 的微调是什么？

### 用户问题

VLM 的微调是什么？我这里指的是针对特定场景的微调？

### 回答整理

VLM 的微调，就是把一个已经具备“看图 + 理解语言 + 生成回答”能力的视觉语言模型，继续用特定场景的数据训练，让它更适合某个业务或任务。

这里说的“针对特定场景的微调”，通常也叫：

- 领域微调
- 场景微调
- 任务微调

例如：

- 工业质检：识别划痕、缺陷、焊点异常
- 医疗影像：根据影像回答特定诊断辅助问题
- 电商：识别商品属性、材质、款式、瑕疵
- 文档/票据：按固定格式抽取字段
- 安防/交通：判断是否违规、识别事件类型
- 自动驾驶：理解特定摄像头视角下的环境、风险和交通行为

VLM 微调通常不是单纯“让模型记住一些知识”，而是让它学会：

- 看懂你的图像分布，例如相机角度、光照、设备、目标外观。
- 理解你的专业标签和判断标准，例如什么算风险、什么算异常。
- 按你的业务格式输出，例如 JSON、分类结果、原因和置信度。
- 减少通用模型在垂直场景里的误判和幻觉。

常见微调方式：

- 全量微调：更新整个模型，成本高、风险大。
- LoRA / QLoRA 微调：只训练少量额外参数，成本低，是常见方案。
- Adapter / projector 微调：只调视觉特征和语言模型之间的连接部分。
- 指令微调：用“图片 + 问题 + 标准答案”的数据，让模型学会按指令回答。
- 分类头/检测头微调：如果目标很固定，也可把 VLM 当特征提取器，再接专门任务模块。

是否值得微调，要看目标：

值得微调的情况：

- 通用 VLM 在你的场景里经常误判。
- 图像风格、专业术语、判断标准很特殊。
- 输出格式必须稳定。
- 有足够高质量标注数据。
- 任务长期稳定。

不一定需要微调的情况：

- 只是想改变回答风格。
- 只是补充文本知识。
- 数据很少，只有几十条样本。
- 任务主要靠外部知识库，而不是视觉判断。
- prompt、规则、RAG、少样本示例已经能达到要求。

一句话总结：

VLM 场景微调 = 用业务里的图像和标准答案，训练模型更懂你的视觉场景、判断规则和输出规范。

## 2. 自动驾驶场景下常见 VLM 基座、微调内容和数据需求

### 用户问题

这里我们重点关注自动驾驶场景的微调。常见的 VLM 基座模型有哪些？Qwen2-VL? Gemini v2? LLaVA? 具体微调是要调什么？我想要微调需要什么数据？比如自驾这里是不是就得有对应场景的数据，尤其是一定数量的长尾数据？

### 回答整理

自动驾驶场景里做 VLM 微调，核心是让模型适应：

- 驾驶视角
- 多相机/视频时序
- 交通参与者
- 风险判断
- 规划语义
- 长尾事件

但要注意：VLM 可以用于感知解释、场景理解、驾驶决策辅助、数据标注/挖掘，不应未经充分验证地直接闭环控制车辆。

### 常见 VLM 基座

| 类别 | 代表模型 | 是否适合自定义微调 |
|---|---|---|
| 开源通用 VLM | Qwen2-VL、Qwen2.5-VL、LLaVA、LLaVA-OneVision、InternVL、MiniCPM-V、PaliGemma、Phi Vision | 适合，尤其适合 LoRA/QLoRA、SFT |
| 闭源商用 VLM | Gemini、GPT-4o/4.1/5 系列视觉能力、Claude Vision 等 | 更适合 prompt/RAG/eval；可微调能力受平台限制 |
| 自动驾驶专用 VLM/数据方向 | DriveLM、NuScenes-QA、BDD-X、DriveBench 等 | 更适合参考任务设计、数据格式和评测 |

### 具体微调是在调什么？

自动驾驶 VLM 微调通常不是“重新训练一个自动驾驶大模型”，而是在已有 VLM 上调整这些部分：

1. 语言模型部分 LoRA/QLoRA

   让模型学会驾驶场景术语、风险判断逻辑、输出格式，例如“左前方电动车横穿，有遮挡风险，建议减速”。

2. 视觉-语言连接层 / projector / adapter

   让视觉特征更好对齐驾驶语义。很多时候先冻结视觉 encoder，只调 projector + LLM LoRA，是比较现实的起点。

3. 视觉 encoder 的部分层

   如果相机视角、鱼眼/环视、夜间、雨雾、红外、低分辨率很特殊，可能需要解冻部分视觉层，但成本和过拟合风险更高。

4. 时序/视频模块

   自动驾驶不是单帧问题。要理解 cut-in、行人意图、车辆加减速、信号灯变化，最好输入连续帧或视频片段。

5. 多传感器/多视角融合模块

   如果要用前视、环视、BEV、LiDAR、Radar、HD map、ego speed，需要额外设计 fusion adapter，而不是直接把图片丢给普通 VLM。

6. 任务头或结构化输出约束

   如果目标是轨迹、控制、风险分级、目标框、JSON 决策，可能需要额外 head 或严格的 supervised output format。

### 需要什么数据？

自驾 VLM 微调的数据最好是：

```json
{
  "images": ["front_t0.jpg", "front_t1.jpg", "front_t2.jpg"],
  "ego_state": {
    "speed_mps": 8.3,
    "yaw_rate": 0.02
  },
  "prompt": "分析当前驾驶风险，并给出下一步驾驶建议，输出 JSON。",
  "answer": {
    "risk_level": "high",
    "key_objects": [
      {
        "type": "pedestrian",
        "location": "front-right",
        "reason": "partially occluded and moving toward ego lane"
      }
    ],
    "suggested_action": "decelerate",
    "explanation": "右前方遮挡区域有行人进入车道风险，当前速度下应提前减速。"
  }
}
```

更系统地说，需要几类数据：

- 基础场景理解数据：天气、时间、道路类型、车道、红绿灯、交通标志、施工区域。
- 目标感知数据：2D/3D box、类别、距离、相对速度、遮挡状态、track id。
- 关系/因果数据：谁影响 ego，谁有冲突风险，为什么需要减速/让行/变道。
- 预测数据：其他车辆/行人未来运动意图。
- 规划/决策数据：ego 下一步动作、轨迹、控制标签、风险等级。
- 解释数据：自然语言 rationale，但要避免让模型学会“编理由”。
- 结构化 QA 数据：例如“前方最危险目标是什么？”“是否可以左变道？”“为什么不能加速？”

### 长尾数据是否关键？

是，非常关键。自动驾驶微调的价值很大程度就在长尾：

- 夜间、雨雪、雾、强逆光
- 施工、临时锥桶、交警手势
- 遮挡行人、儿童、轮椅、异形车辆
- emergency vehicle、校车、事故车
- 非保护左转、无保护右转、复杂路口
- cut-in、急刹、鬼探头
- 地图不一致、车道线缺失、信号灯异常
- 罕见交通标志、区域性交通规则

但长尾数据不是“越多越好”。更重要的是：

- 覆盖矩阵：按天气、道路、光照、交通密度、对象类型、风险类型分桶。
- 高质量标注：长尾样本少，错标会非常伤。
- hard negative：看起来危险但其实安全、看起来正常但实际危险的样本都要有。
- 比例控制：长尾要增强，但不能把模型调到过度保守，导致到处误报。
- 独立评测集：长尾训练集和长尾测试集必须拆开，否则只是记忆场景。

建议路线：

1. 先选开源基座：Qwen2.5-VL / Qwen2-VL、LLaVA-OneVision、InternVL。
2. 第一阶段只做 SFT + LoRA：冻结视觉 encoder，调 projector/LLM LoRA。
3. 任务先别做“端到端开车”，先做风险识别、场景 QA、关键目标解释、是否可变道/是否需减速、JSON 结构化输出。
4. 数据先从公开数据集 + 自有场景日志构建 QA/解释/风险标签。
5. 长尾数据单独建 benchmark，训练时采样增强，评测时独立统计。

一句话总结：

自动驾驶 VLM 微调不是简单让模型“看更多路况图片”，而是用多帧、多视角、带驾驶语义标注的数据，让模型学会识别关键交通参与者、理解风险因果、输出稳定的驾驶语义判断。长尾数据不是锦上添花，而是这个方向是否有价值的核心。

## 3. 常用微调方法推荐

### 用户问题

常用的微调方法是什么？你能给我推荐几个吗？

### 回答整理

常用方法可以分成两层：训练策略和调哪些模块。自动驾驶场景建议优先从轻量、可控的路线开始。

### 常见微调方法

1. SFT / 视觉指令微调

   最常用。数据形式是“图像/视频 + 问题/指令 + 标准答案”，让 VLM 学会驾驶任务，比如风险识别、关键目标解释、是否可变道、是否需要减速。

2. LoRA

   冻结大部分基座模型，只在 Transformer 层插入低秩可训练参数。优点是成本低、部署方便，适合多任务/多场景分别训练 adapter。

3. QLoRA

   和 LoRA 类似，但把基座模型量化到 4-bit，再训练 LoRA adapter。适合 GPU 资源有限时做 VLM 微调。

4. Projector / Adapter 微调

   VLM 通常有视觉 encoder、语言模型、视觉-语言连接层。数据量不大时，可以先只调连接层或 adapter，让视觉特征更适配驾驶语义。

5. 部分解冻视觉 encoder

   如果摄像头域差异很大，比如鱼眼、环视、夜间、雨雾、低照度、车载特定视角，可以解冻视觉 encoder 的后几层。但这更贵，也更容易过拟合。

6. 视频/时序微调

   自动驾驶很多问题不是单帧能解决的，比如 cut-in、行人意图、前车急刹、信号灯变化。单帧 VLM 只能看状态，视频/多帧才能看趋势。

7. DriveLM-style Graph VQA 微调

   很适合自动驾驶 VLM 的任务组织方式。不是只问“图里有什么”，而是把问题拆成感知、预测、规划、行为、轨迹等链式 QA，让模型学驾驶推理过程。

8. DPO / 偏好微调

   在 SFT 后使用“好答案 vs 坏答案”训练模型偏好。自驾里可以用来压制幻觉、过度自信、不安全建议、格式错误答案。

### 推荐方案

方案 A：最推荐起步

```text
Qwen2.5-VL / InternVL / LLaVA-OneVision + SFT + LoRA
```

适合先验证场景微调是否有效。训练内容是冻结视觉 encoder，训练 LLM LoRA，必要时训练 projector。任务包括风险识别、关键目标、驾驶建议、JSON 输出。

方案 B：资源有限

```text
Qwen2.5-VL-7B 或更小模型 + QLoRA
```

适合单机或较少 GPU。优点是显存压力小，能快速试验数据配方。缺点是极端视觉域适配能力有限，不适合一上来做复杂闭环驾驶。

方案 C：自动驾驶语义推理

```text
开源 VLM + DriveLM-style Graph VQA SFT
```

数据不要只做普通 caption，而要做链式问题：

- 哪些对象和 ego vehicle 有交互？
- 最危险目标是谁？
- 为什么危险？
- 未来 2-3 秒可能发生什么？
- ego 应该减速、停车、保持还是变道？
- 输出依据是什么？

方案 D：视频场景

```text
Video VLM / 多帧 VLM + LoRA/SFT
```

如果关心 cut-in、鬼探头、行人意图、信号灯变化，就应该用多帧。

方案 E：上线前对齐

```text
SFT 后再做 DPO
```

先让模型会做任务，再用偏好数据修正行为。例如同一场景下：

- chosen：指出遮挡风险，建议减速，输出保守但合理。
- rejected：忽略遮挡，建议保持速度，或者编造不存在目标。

推荐顺序：

1. 先做 SFT + LoRA。
2. 数据格式用驾驶 QA / JSON。
3. 加入长尾和 hard negative。
4. 单帧跑通后再上多帧。
5. 效果稳定后再考虑 DPO。
6. 最后才考虑解冻视觉 encoder 或做多传感器 fusion。

一句话总结：

自动驾驶 VLM 微调最推荐从“DriveLM-style 数据组织 + SFT + LoRA/QLoRA”开始。不要一开始全量微调，也不要直接追求端到端控制。

## 4. DINOv3 + 自建文本塔 / Qwen 文本塔，这算不算微调？

### 用户问题

我之前做过一个实验，但是 base DINOv3-ViT-L 模型，然后我希望它能获得图像文本对齐的功能，我的图像塔沿用 DINOv3 的模型，但是文本塔是从零开始训练，然后又设计了一个两个模型的接口。这样算是微调吗？如果我文本塔直接用 Qwen-VL 的文本塔，然后只是设计接口，算是微调吗？

### 回答整理

第一个实验严格说不太算“微调”，更准确叫：

```text
基于冻结/半冻结视觉基座的多模态对齐训练
```

或者：

```text
从 DINOv3 视觉塔出发训练一个新的图文模型
```

DINOv3 本身是自监督视觉基座，重点是提供强视觉特征。你在它外面加文本塔和接口，让它获得图文对齐能力，本质是在做 vision-language alignment，不是典型的“微调已有 VLM”。

可以按“哪些参数被更新”来定义：

| 方案 | 训练什么 | 严格分类 |
|---|---|---|
| DINOv3 冻结，文本塔从零训练，接口训练 | 新文本塔 + 跨模态接口 | 多模态对齐预训练，不是 DINOv3 微调 |
| DINOv3 部分解冻，文本塔从零训练，接口训练 | DINOv3 + 新文本塔 + 接口 | DINOv3 的领域/跨模态微调 + 新模型训练 |
| DINOv3 冻结，文本塔用 Qwen/Qwen-VL，接口训练 | 只训练 connector/projector | adapter/projector 训练，严格说不是基座微调 |
| DINOv3 冻结，Qwen 文本塔 LoRA，接口训练 | Qwen 文本侧 LoRA + connector | 参数高效微调，也可称 VLM 微调 |
| DINOv3 LoRA/部分解冻，Qwen 也 LoRA，接口训练 | 视觉塔 + 语言塔 + 接口 | 真正的多模态联合微调 |
| 全部参数都更新 | 全模型 | 全量 VLM 微调/继续预训练 |

所以第一个实验：

```text
base DINOv3-ViT-L，图像塔沿用 DINOv3，文本塔从零开始训练，再设计两个模型接口。
```

如果 DINOv3 没有更新参数，那不是“微调 DINOv3”，而是：

```text
用 DINOv3 做视觉特征提取器，训练一个新的文本塔和图文对齐模块。
```

如果训练了 DINOv3 的一部分，比如最后几层、LoRA、adapter，那才可以说：

```text
对 DINOv3 做了图文对齐方向的微调。
```

第二个问题：

```text
如果文本塔直接用 Qwen-VL 的文本塔，然后只是设计接口，算是微调吗？
```

如果只是训练接口，例如 projector、MLP、Q-Former、cross-attention adapter，而 DINOv3 和 Qwen 文本塔都冻结，那严格说也不是微调基座模型，而是：

```text
冻结双塔 + 训练跨模态连接器。
```

但在工程口径里，有些人会宽泛地说这是“微调一个 VLM 系统”，因为整个系统里有一部分参数被训练了。更精确的说法应该是：

```text
connector tuning / adapter tuning / multimodal alignment tuning
```

关键区别是：

```text
有没有更新已有预训练模型的权重？
```

如果没有，只训练新加模块，就不是严格意义上的 fine-tuning base model。

建议表述：

版本 1：DINOv3 + 从零文本塔

```text
我们冻结/沿用 DINOv3 作为视觉塔，训练文本塔和跨模态对齐接口，使模型获得图文对齐能力。该过程更接近多模态对齐预训练，而不是传统微调。
```

版本 2：DINOv3 + Qwen/Qwen-VL 文本塔

```text
我们使用 DINOv3 作为视觉塔、Qwen 系列模型作为语言/文本塔，训练视觉到语言空间的 connector。如果语言塔和视觉塔冻结，则属于 connector tuning；如果进一步对 Qwen 或 DINOv3 加 LoRA/解冻训练，则属于参数高效 VLM 微调。
```

重要判断：

如果文本塔从零开始训练，成本会非常高，因为它不仅要学图文对齐，还要从头学语言语义。对于自动驾驶场景，更建议：

1. DINOv3 视觉塔冻结或 LoRA。
2. Qwen/Qwen2.5/Qwen-VL 的语言部分作为文本/语言基座。
3. 训练 projector / Q-Former / cross-attention adapter。
4. 再用自驾 QA、风险判断、场景解释数据做 SFT。
5. 必要时再对语言塔或视觉塔做 LoRA。

一句话总结：

之前做的是“图文对齐训练/多模态预训练”，不一定是微调；只有当你更新了 DINOv3、Qwen 或 Qwen-VL 这些已有基座的参数时，才严格算微调。

## 5. 商用 Gemini v2 权重场景下，微调的是全量权重还是部分权重？

### 用户问题

比如我们现在商用，有了 Gemini v2 的具体模型，同时我们通过购买获得了对应的权重参数等，之后我们要进行微调。那么这里微调的是全量的模型权重吗？还是只开放后续的几层进行调整？这里需要修改模型吗？还是说只是同样的模型基础上让它适应新的数据？

### 回答整理

如果说的是 Google 官方 Gemini 商用服务，需要先澄清：普通 Gemini API / AI Studio 并不是传统意义上的“客户拿完整权重自己改”。Gemini 的 supervised tuning 主要是平台化能力，且通常更接近 adapter/参数高效微调，而不是客户直接拿全量权重做全量反向传播。

如果确实通过商业授权拿到了“权重参数”，要分三种情况看。

### 1. 全量微调

更新整个模型的所有权重：

```text
vision encoder + projector + LLM + 可能的时序模块 全部参与训练
```

理论上可以，但商用大 VLM 上很少这么干。原因是：

- 显存和算力成本极高。
- 容易灾难性遗忘。
- 安全对齐能力可能被破坏。
- 训练后模型评估和合规成本很高。
- 很多商业授权不会允许改完整基座权重。

除非是模型厂商级别的训练团队，否则一般不推荐。

### 2. 部分层微调

只开放后几层或关键模块，例如：

```text
冻结大部分模型
只训练最后 N 层 Transformer
只训练视觉-语言 projector
只训练 cross-attention / adapter
只训练 temporal adapter
```

这比全量微调现实很多。自动驾驶场景里，如果只是让模型更懂驾驶语义、风险判断、输出格式，通常不需要动全部权重。

### 3. LoRA / Adapter 微调

这是最常见的商用路线：

```text
base model 冻结
额外插入 LoRA / adapter 参数
训练这些小参数
推理时加载 base model + adapter
```

这种情况下，严格说原始模型权重没有被改，但整个系统的行为被微调了。很多平台所谓的 fine-tuning，实际就是这种 adapter tuning。

核心结论：

```text
微调一般不是默认全量调整模型权重。
```

在商业大模型场景里，更常见的是：

```text
冻结基座，只训练 adapter / LoRA / projector / 后几层。
```

### 是否需要修改模型结构？

不需要改模型结构的情况：

- 输入还是图像/视频 + 文本。
- 输出还是文本/JSON/分类标签。
- 只是希望模型适应自动驾驶数据、术语、判断标准。
- 只是让它更稳定地回答“是否危险、为什么、该怎么做”。

这时就是在同一个模型基础上，用新数据做 SFT/adapter tuning。

需要改模型结构的情况：

- 要接入多相机环视、BEV、LiDAR、Radar、HD map、ego state。
- 要输出轨迹、控制量、3D box、occupancy grid。
- 要做多帧时序建模，而原模型只适合单图。
- 要替换视觉塔，比如换成 DINOv3。
- 要增加专门的规划头、检测头、风险评分头。

自动驾驶里更实际的方案通常是：

```text
Gemini/VLM 基座冻结
+ 自驾数据 SFT
+ adapter/LoRA
+ 必要时加多帧/多视角接口
+ 严格评测长尾场景
```

如果只是“让 Gemini v2 更适应我们自驾场景的数据”，那更像是：

```text
同一模型架构
不改或少改结构
训练一组 adapter/LoRA/后层参数
得到一个 tuned model
```

而不是：

```text
重新设计 Gemini
全量更新所有权重
训练出一个新基础模型
```

内部文档建议写清楚：

- Full fine-tuning：更新全量权重，成本最高，风险最大。
- Partial fine-tuning：只解冻部分层。
- PEFT / LoRA / Adapter tuning：冻结基座，训练小模块，最推荐。
- Connector tuning：只训练接口层，适合接入新视觉塔或新传感器。

对自动驾驶场景，第一阶段建议选择：

```text
基座冻结 + projector/adapter + LoRA + 自驾 SFT 数据
```

除非这个方案在长尾评测上明显不够，再考虑解冻视觉后层或时序模块。
